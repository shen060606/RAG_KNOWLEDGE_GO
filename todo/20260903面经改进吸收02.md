## 二、第二份面经中的 RAG 重点

## 1. 关键词/查询重写如何做对比实验

### 当前项目状态

当前没有查询重写模块。`rag.AskThreeSteps` 直接对用户原问题进行 Embedding 并检索，因此“它有哪些优点”“那第二种呢”等依赖上下文的追问容易召回失败。

这里更准确的名字是“查询重写”，不只是抽取关键词。目标是将依赖对话上下文的问题改写为语义完整、适合检索的独立查询。例如：

```text
上一轮：Qdrant 和 pgvector 有什么区别？
当前问题：它在权限过滤上有什么优势？
重写结果：Qdrant 在基于 payload 的用户权限过滤上有什么优势？
```

### 对比实验应该怎么做

必须使用同一份语料、同一套 Chunk、同一个 Embedding 模型和相同 TopK，只改变是否重写：

```text
A 组：原始问题 -> Embedding -> 检索
B 组：原始问题 + 最近对话 -> 查询重写 -> Embedding -> 检索
```

每条评测数据至少包含：

```json
{
  "id": "rewrite-001",
  "history": [
    {"role": "user", "content": "介绍一下 Qdrant"},
    {"role": "assistant", "content": "..."}
  ],
  "question": "它如何实现用户隔离？",
  "gold_query": "Qdrant 如何通过 payload filter 实现用户向量数据隔离？",
  "relevant_chunk_ids": [120001, 120002],
  "reference_answer": "...",
  "answerable": true,
  "category": "coreference"
}
```

### 召回率的判断标准

不是“有没有返回结果”，也不是“返回数量越多越好”。向量数据库几乎总能返回 TopK，哪怕它们与问题无关。

正确标准是：TopK 中是否包含人工标注的相关 Chunk，以及相关 Chunk 的排名是否靠前。

核心指标：

- `Hit@K`：TopK 是否至少命中一个标准相关 Chunk。
- `Recall@K`：标准相关 Chunk 中有多少被 TopK 找到。
- `Precision@K`：TopK 中有多少是真正相关的结果。
- `MRR`：第一个相关 Chunk 排名越靠前越好。
- `NDCG@K`：存在多级相关性标注时，评价整体排序质量。
- 无答案误召回率：本应拒答的问题是否被错误资料“强行回答”。

示例：标准相关 Chunk 是 `{A, B}`，Top5 返回 `{X, A, Y, Z, B}`，则 Hit@5=1、Recall@5=1、Precision@5=0.4，第一个正确结果排名为 2，RR=0.5。

### 如何量化重写后变好还是变差

对每条问题同时运行 A/B 两组，记录：

- 原查询和重写查询。
- 两组召回 Chunk ID、score 和排名。
- Hit@K、Recall@K、MRR、NDCG 的差值。
- 重写耗时、总检索耗时和额外 Token/费用。
- 最终答案的正确性、忠实度和引用准确率。

除了平均值，还要分类统计：

- 指代消解问题是否明显提升。
- 独立问题是否被过度重写而退化。
- 专有名词、编号和代码符号是否被错误改写。
- 无答案问题是否因重写产生错误召回。

建议判定规则：先定义门槛，例如 Recall@5 提升、MRR 不下降、独立问题退化率低于约定阈值、P95 延迟增量可接受，再决定上线。门槛必须结合真实基线设定，不能先编造提升百分比。

### 是否可以只手工测试少量 Case

少量 Case 只适合开发调试，不能证明整体效果。推荐构建约 150 条可版本化数据，并通过脚本批量运行：

- 50 条独立完整问题。
- 40 条代词/省略追问。
- 20 条多实体歧义问题。
- 20 条精确关键词、编号或代码查询。
- 20 条无答案或越权数据问题。

人工负责标注和抽查，脚本负责可重复运行、聚合指标、保存失败样本。模型可以作为辅助 Judge，但不能替代人工 Gold Chunk 和关键坏例复核。

## 2. 滑动窗口与摘要压缩

### 当前项目状态

当前 `database.GetSessionHistory` 加载整个会话的全部历史，没有滑动窗口和摘要。会话增长后会增加数据库读取量、Prompt Token、模型费用和 TTFT，也可能让旧话题干扰当前回答。

### 摘要压缩的核心目的

主要目的不是降低数据库存储成本。原始聊天记录仍应保存在 MySQL 中，便于审计、重新摘要和恢复。摘要的主要目标是减少每次推理携带的上下文 Token，从而控制上下文窗口、降低推理延迟和调用费用，并减少无关历史干扰。

推荐上下文结构：

```text
system 指令
长期结构化记忆（关键实体、用户约束、未完成事项）
较早历史的滚动摘要
最近 2～4 轮原始对话
本次检索上下文
当前问题
```

### 如何避免关键信息丢失

不要只生成一段自由文本摘要，使用“结构化记忆 + 摘要 + 最近原文”：

```json
{
  "entities": {
    "database": "Qdrant",
    "project": "rag_knowledge"
  },
  "user_preferences": [],
  "decisions": ["私有向量按 user_id 隔离"],
  "constraints": ["回答必须引用来源"],
  "open_tasks": ["增加混合检索"],
  "summary": "用户正在讨论 RAG 检索优化。"
}
```

保护措施：

- 用户名、项目名、实体 ID、时间、数值、约束和否定信息作为结构字段抽取，不完全依赖自由摘要。
- 最近若干轮保留原文，短期指代不经过摘要。
- 摘要更新时同时提供旧摘要和新离开窗口的消息，避免每次从零压缩。
- 原始消息不删除；发现回答缺上下文时可以按关键词或 Embedding 回查历史。
- 摘要带版本号和覆盖消息范围，失败时退回最近消息窗口。
- 建立长对话评测集，专门检查实体保持率、约束保持率和指代正确率。

如果中途发现关键信息缺失，系统应先检索历史消息；仍无法确定时向用户澄清，不能自行补全。

## 3. RAG 评测集如何标注答案

检索效果和生成效果必须分开评估：

### 检索标注

- 人工根据原文确定问题是否可回答。
- 标注所有足以支撑答案的 Gold Chunk，而不是只标一个“看起来最像”的 Chunk。
- 必要时使用 0/1/2 等相关性等级：不相关、部分相关、完全支撑。
- 文档重新切块后需要重新映射 Gold Chunk，可用文档位置或内容哈希辅助迁移。

### 生成答案标注

- `reference_answer` 是参考事实集合，不要求模型逐字匹配。
- 同时检查正确性、完整性、忠实度、引用准确性和无答案拒答。
- 数值、实体名、权限结论等关键字段可以用确定性规则校验。
- 开放表达可用 LLM-as-a-Judge 做语义评分，但 Judge Prompt、模型和版本必须固定，并要求输出评分理由和引用证据。
- 抽样人工复核 Judge 结果，计算人与模型的一致性；重要结论不能只依赖单个 Judge 模型。

推荐评分组合：

```text
最终评分 = 检索指标 + 事实规则校验 + LLM 语义评分 + 人工坏例复核
```

不要使用简单字符串完全匹配评价自然语言答案，也不要仅凭 LLM 打一个总分。

## 三、面经提到但当前项目未实现的能力

## 1. MCP 工具调用安全

### 当前项目状态

当前项目没有 MCP、Function Calling 或模型自主工具调用。LLM 只能接收 Prompt 并生成文本，因此面试时不能声称已经实现 MCP 防注入。

如果未来增加 MCP，安全边界不能只靠正则或敏感词拦截。模型输出和工具返回都必须视为不可信数据。

### 推荐的纵深防御

1. **固定工具白名单**：只注册业务需要的工具，模型不能传入可执行命令或任意 URL。
2. **结构化参数**：使用严格 JSON Schema；拒绝未知字段、超长输入和类型不符参数。
3. **禁止通用 Shell 工具**：将能力封装为 `ListDocuments(userID)` 等窄接口，不提供 `exec(command)`。
4. **服务端权限校验**：userID 从已验证 Session 注入，绝不能接受模型参数里的 userID。
5. **资源级鉴权**：工具执行前校验文档 owner、角色、租户和操作权限。
6. **高风险动作确认**：删除、覆盖、修改权限等操作需要用户二次确认、幂等 Key 和审计日志。
7. **运行隔离**：文件、网络、CPU、内存、超时和调用次数最小授权；敏感服务使用独立凭据。
8. **结果校验**：限制返回大小和 MIME；敏感字段脱敏；工具输出只作为数据，不能作为更高优先级指令。
9. **循环保护**：设置最大工具调用次数、总耗时和费用预算，防止 Agent 无限循环。
10. **审计与测试**：记录调用者、工具、参数摘要、授权结果和副作用；使用 Prompt Injection、越权和 SSRF 用例回归。

调用流程：

```text
模型提出 Tool Call
  -> 工具名白名单
  -> JSON Schema 校验
  -> 从服务端身份上下文注入 userID
  -> RBAC + 资源归属校验
  -> 风险分级/必要时用户确认
  -> 沙箱或受限服务执行
  -> 输出大小、格式、敏感信息校验
  -> 记录审计日志
  -> 结果以“不可信数据”返回模型
```

## 2. 租约锁与任务续约

### 当前项目状态

当前项目没有分布式租约锁，也没有异步文档任务。这个问题可作为未来异步入库、重复消费和定时清理的工程扩展题准备。

### 推荐设计

租约锁应具有 `owner_token + TTL + fencing_token`：

- 获取锁使用原子 `SET lock_key owner_token NX PX ttl`。
- 续约必须执行 Lua/事务式 compare-and-expire：只有锁值仍等于自己的 owner token 才能延期。
- 解锁必须 compare-and-delete，避免删除别人重新获得的锁。
- fencing token 单调递增，下游写操作拒绝旧 token，解决暂停线程恢复后继续写的问题。

不建议让完全独立的续约线程只看“进程还活着”就无限续锁，因为业务线程可能已经死锁或永久卡住。更合理的方案是：

- 业务任务持续更新进度或 heartbeat。
- watchdog 只有观察到任务进度且未收到取消信号时才续约。
- 每次外部调用和阶段处理必须有超时。
- 设置任务最大执行时长和最大续约次数。
- 业务完成后停止续约并释放锁；不是“消费完成后再续锁”。
- 锁过期后任务允许被重新领取，处理逻辑必须幂等。

可续约阶段：解析大文件、批量生成 Embedding、批量写向量时按耗时或批次上报进度。不要在业务已经结束后续约。

如果主线程卡死：watchdog 因看不到进度而停止续约，TTL 到期后锁自动释放；任务被其他 Worker 重新领取。原 Worker 即使恢复，下游也通过 fencing token 拒绝它的过期写入。

## 3. RocketMQ 延迟消息、领券和订单超时

这些不是当前 RAG 项目的功能，不应加入项目经历。可以作为中间件与延时任务八股准备，也能迁移到“文档过期清理、失败任务重试、Session 清理”等场景。

### 固定延时不能满足精确时间怎么办

- 使用支持任意时间戳的定时消息能力（具体能力需以所用 RocketMQ 版本为准）。
- 只支持固定等级时，选择最接近的较短等级，到期前再次投递或由消费者检查目标时间；会增加消息次数和误差。
- 使用时间轮、Redis ZSet、数据库任务表或专门的调度服务保存精确到期时间。
- 无论哪种方案，消费者都必须幂等，并校验业务当前状态，不能仅凭超时消息直接关闭订单。

### 延迟队列核心设计

```text
生产者写入任务（task_id, execute_at, payload）
  -> 按到期时间排序存储
  -> 调度器只关注最近一批任务
  -> 到期后原子取得任务所有权
  -> 投递普通消息/执行回调
  -> 消费者幂等处理
  -> 成功确认；失败重试；超过次数进入死信队列
```

底层常见数据结构包括分层时间轮、最小堆、按时间分桶的队列和 Redis ZSet。大量延迟消息不能为每条消息创建独立线程或定时器。

### 订单 15 分钟关闭方案

- MQ 延迟/定时消息：扩展性好，需处理重复、丢失和消息提前/延后。
- Redis ZSet：score 为过期时间，Worker 原子领取到期订单；需要高可用和补偿扫描。
- 数据库任务表 + 分片扫描：实现直观、可靠性容易与业务库结合，但有轮询压力。
- 时间轮：高吞吐、内存效率高，但进程重启恢复和分布式协调较复杂。
- 调度平台：适合可观测、可重试的任务，但海量逐订单任务需要评估容量。

如果明确禁止成熟延迟消息和数据库轮询，可答 Redis ZSet、持久化时间轮或调度服务。任何方案最终都要解决持久化、重启恢复、重复执行、幂等、取消、重试、死信和时间误差。

关闭订单时使用条件更新：只有 `status=UNPAID` 且版本匹配才能改为 `CLOSED`；即便超时消息与支付消息竞态，也不会关闭已支付订单。

## 五、八股题思路提示

## 1. 微信电脑端扫码登录

核心是二维码只包含短期、一次性的 login token，不直接包含账号凭证。

```text
电脑请求二维码 -> 服务端创建 WAIT_SCAN 状态和短期 token
手机扫码 -> 手机已登录身份请求服务端，状态变为 SCANNED
手机确认 -> 服务端状态变为 CONFIRMED，并绑定账号
电脑获知确认 -> 用一次性凭证换取自己的 Session
二维码 token 立即失效
```

电脑感知状态可用短轮询、长轮询、SSE 或 WebSocket。扫码登录只有单向状态通知，SSE/长轮询通常足够；要处理过期、拒绝、重复确认、跨设备绑定和一次性消费。

## 2. SSO 是什么

单点登录是在统一认证中心登录一次后访问多个互相信任的系统。重点区分：

- 认证中心负责确认用户身份。
- 业务系统负责自己的授权。
- 常见协议是 OAuth 2.0（授权）、OpenID Connect（身份认证）、SAML。
- 还要考虑单点登出、Token 过期、刷新、签名验证、audience 和重放攻击。

## 3. 等待所有子线程结束

Java 可使用：

- `Thread.join()`：线程少、关系简单。
- `CountDownLatch`：主线程等待 N 个任务完成，子任务在 `finally` 中 `countDown()`。
- `ExecutorService.invokeAll()` / 收集 `Future.get()`。
- `CompletableFuture.allOf(...).join()`：异步任务编排。
- `ForkJoinPool`：递归拆分任务。

回答时补充异常、超时、线程池关闭和中断处理。

## 4. 并发 i++ 如何保证安全

`i++` 实际包含读取、加一、写回，多线程交错会丢失更新，因此不是原子操作。

可选方案：

- `synchronized` 或 `Lock` 保护临界区。
- `AtomicInteger.incrementAndGet()` 使用 CAS，低竞争时更轻量。
- `LongAdder` 将热点拆散，高竞争统计吞吐更好，但读取到的是汇总值，不适合要求每次严格线性一致的序号。

CAS 要说明自旋、竞争下 CPU 开销和 ABA 问题；Java 常用 `AtomicInteger`、`AtomicLong`、`AtomicReference`，带版本可用 `AtomicStampedReference`。

## 5. 多线程各自独立计数

如果变量在语义上就不应共享，使用线程本地存储：Java `ThreadLocal<Integer>`。每个线程设置自己的初始值并独立自增，使用完在 `finally` 中 `remove()`，防止线程池复用造成数据残留。更简单的场景直接使用任务方法内的局部变量，通常优于 ThreadLocal。

## 6. synchronized 锁信息存在哪里

HotSpot 对象通常由对象头、实例数据和对齐填充组成。锁相关状态主要记录在对象头的 `Mark Word` 中；它会复用存储哈希、GC 年龄和锁状态等信息。具体位布局依赖 JVM 实现、位数、压缩指针和版本，不要死背一个对所有版本都成立的位数图。

## 7. MySQL 联合索引与最左前缀

B+Tree 联合索引 `(A, B)` 先按 A 排序，A 相同时再按 B 排序，所以无法在缺少 A 约束时直接利用整棵树快速定位 B。

`WHERE B=1 AND A=2` 一般可以使用 `(A,B)`，因为优化器会重排等值条件，SQL 中书写顺序不决定索引顺序。`WHERE B=1` 通常不能有效利用该联合索引的最左前缀，但具体计划应以 `EXPLAIN ANALYZE` 为准。

建索引前考虑：查询频率、过滤比例、回表次数、排序/分组、覆盖索引、写放大、磁盘占用和现有索引重复。区分度可用 `COUNT(DISTINCT col) / COUNT(*)` 粗略量化，但不能只看区分度，还要看查询分布和组合条件。

## 8. SQL 注入与 PreparedStatement

核心是参数化查询：SQL 结构与参数值分离，参数按数据类型绑定，不再被解释为 SQL 语法。还需要：

- 表名、列名和排序方向不能直接参数化时使用白名单映射。
- 最小权限数据库账号。
- 不拼接动态 SQL，不依赖转义或关键词过滤。
- 错误信息不向客户端暴露内部 SQL。

当前 Go 项目使用 GORM 的 `Where("user_id = ?", userID)` 属于参数绑定思路；若将用户输入拼到 SQL 字符串中仍会有风险。

## 9. Redis 与 MySQL 双写一致性

除了 Cache Aside，还可回答：

- 延迟双删：更新 DB，删缓存，延迟后再删一次；仍需处理窗口与失败。
- 事务消息/消息队列：DB 更新后通过 Outbox 投递失效事件，消费者删或更新缓存。
- 订阅 binlog/CDC：监听数据库变更刷新或删除缓存。
- Write Through：应用写缓存，由缓存层同步写数据库。
- Write Behind：缓存异步落库，吞吐高但丢数据和一致性风险更大。

实践重点是以数据库为准、缓存操作幂等、失败重试和最终一致性。当前项目 Redis 只缓存文本到 Embedding 的确定性结果，不是典型业务数据双写，但模型版本必须进入缓存 Key。

## 10. Redis 是多线程吗

不能只答“单线程”。Redis 核心命令执行长期以单线程事件循环保证顺序，但后台持久化、异步释放、网络 I/O 等可使用其他线程；较新版本也支持 I/O 线程。重点是命令执行模型与整个进程是否只有一个线程是两个问题。

## 11. Redis 过期 Key 删除策略

- 惰性删除：访问 Key 时发现过期再删除。
- 定期删除：周期性抽样检查并删除过期 Key。
- 内存达到上限时还会触发淘汰策略，但“过期删除”和“内存淘汰”不是同一概念。

只使用惰性删除会积累无人访问的过期 Key，只使用全量定时扫描成本又过高，因此 Redis 组合使用惰性与定期删除。

完成要求：能说清 TSP 与 LeetCode 847 的关键区别，并独立完成一个小规模状态压缩版本。
