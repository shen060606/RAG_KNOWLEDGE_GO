## 一、当前项目基线（回答面试问题时先讲事实）

### 1. 业务背景与目标用户

当前项目是一个基于 Go + Gin 的多用户 RAG 知识库原型，目标用户是需要上传个人资料并基于资料问答的普通用户，以及负责维护公共知识库的管理员。

主要痛点：

- 通用大模型不了解用户私有文档，直接回答容易过时或产生幻觉。
- 不同用户的私有文档、聊天记录和向量数据必须隔离。
- 管理员维护的公共知识需要被所有已登录用户共享检索。
- 回答需要流式返回并展示引用来源，提高可追溯性。

当前完成度：本地可运行的 V6 原型，已经具备注册登录、Session 鉴权、文档上传、TXT/Markdown/PDF 文本提取、固定长度切块、Embedding 缓存、Qdrant 向量检索、多轮会话、SSE 流式回答、来源展示、私有/公共知识隔离及文档删除。是否真正部署到测试或生产环境需要按实际情况回答，不能把“本地可运行”描述为“已经上线”。

核心代码：

- 路由与依赖组装：`internal/api/router.go`、`main.go`
- 文档上传与解析：`internal/api/handler/upload.go`、`internal/uploads/upload.go`
- 切块与 RAG 编排：`internal/chunker/chunker.go`、`internal/rag/rag.go`
- Embedding 与缓存：`internal/embedder/embedder.go`、`internal/embedder/cache.go`
- 向量存储：`internal/store/store.go`、`internal/store/qdrant.go`
- 对话与流式输出：`internal/api/handler/chat.go`、`internal/llm/llm.go`
- 元数据和用户隔离：`internal/database/models.go`、`internal/database/db.go`

### 2. 当前真实链路

文档入库：

```text
上传文件
  -> Session 鉴权并取得 userID/role
  -> 清理文件名、校验扩展名、检查同用户同名文档
  -> 保存 uploads/<userID>/<filename>
  -> 提取 TXT/MD/PDF 文本
  -> 按 500 rune 固定长度 + 50 rune overlap 切块
  -> Redis Cache-Aside 获取或生成 Embedding
  -> 写入 Qdrant（payload: user_id/filename/is_public/text）
  -> 写入 MySQL documents 元数据
```

提问查询：

```text
用户问题
  -> 按 userID + sessionID 加载全部历史消息
  -> 问题 Embedding
  -> Qdrant TopK=5 向量检索
     filter = 当前用户私有数据 OR 公共数据
  -> 拼接检索上下文与引用编号
  -> 将历史消息 + 当前 RAG Prompt 发给 DeepSeek
  -> SSE 推送 token、sources、done
  -> MySQL 保存用户问题和模型回答
```

当前没有实现：问题改写、问题拆分、意图路由、关键词/BM25 检索、Rerank、相关性阈值、上下文压缩、自动化 RAG 评测和 Agent 工具调用。因此面试中应称为“带多轮记忆的 RAG 应用”，不能称为 Agent，也不能声称已经实现完整高级链路。

## 二、按优先级执行的改进 TODO

## P0：先解决正确性、安全性与可评测性

### [ ] P0-1 建立最小 RAG 评测集与基线

原因：当前没有测试文件和效果指标，无法证明切块、TopK 或模型调整是否真正提升效果。

实施步骤：

1. 选取 10～20 份有代表性的文档，构造至少 50 个问题。
2. 每条样本记录：`question`、`expected_chunk_ids`、`reference_answer`、`answerable`、`category`。
3. 问题类型覆盖事实型、跨段型、同义改写、指代追问、无答案、权限隔离。
4. 由人工先根据原文标注标准答案和应召回 Chunk；有歧义的样本进行二次复核。
5. 固定 Embedding 模型、数据版本和参数，保存首版基线结果。

建议指标：

- 检索：Hit Rate@K、Recall@K、MRR、NDCG@K。
- 生成：答案正确性、忠实度（是否被检索上下文支持）、完整性、引用准确率、拒答准确率。
- 性能：Embedding 延迟、检索延迟、LLM TTFT、总耗时、Prompt Token 数、错误率。
- 权限：其他用户私有 Chunk 泄漏率必须为 0。

验收标准：执行一个命令可生成 JSON/Markdown 评测报告；每次调整检索策略都能与基线比较，不再仅凭主观体验判断。

涉及位置：建议新增 `internal/evaluation/`、`testdata/evaluation/`，并给 `internal/chunker`、`internal/store`、`internal/rag` 增加单元测试。

### [ ] P0-2 修复文档导入的跨存储一致性

原因：当前流程先保存物理文件，再逐个写 Qdrant，最后写 MySQL。解析、Embedding、某个 Chunk 入库或 MySQL 写入失败时，会残留文件或部分向量；`status=processing` 也没有真正用于状态机。

实施步骤：

1. 上传后先创建 `processing` 文档记录并取得稳定 `document_id`。
2. Qdrant payload 增加 `document_id`、`chunk_index`、`content_hash`。
3. 全部 Chunk 成功后将文档更新为 `ready`。
4. 任一步失败执行补偿清理：按 `document_id` 删除向量、删除临时文件、将状态改为 `failed` 并记录错误。
5. 文件先写临时路径，完成后原子重命名到正式路径。
6. 增加失败重试和定期扫描孤儿文件/孤儿向量的修复任务。

验收标准：人为模拟第 N 个 Chunk 写入失败、MySQL 写入失败和进程中断，系统均不会向用户暴露半成品，且可重试恢复。

关键函数：`handler.UploadHandler`、`rag.ImportDoc`、`database.CreateDocument`、`store.Store`。

### [ ] P0-3 强化上传安全

原因：当前主要依据文件扩展名放行，尚缺文件大小限制、内容签名/MIME 校验、压缩炸弹与恶意 PDF 防护；解析失败后还会残留已保存文件。

实施步骤：

1. 在 Gin/HTTP 层使用 `MaxBytesReader` 限制请求体，并设置单文件大小上限。
2. 同时校验扩展名、MIME 和 magic bytes，不信任客户端文件名与 `Content-Type`。
3. 对 PDF 设置页数、提取文本量、解析耗时和内存上限；解析放入受限任务。
4. 拒绝空文件、空文本、异常长单行文本和可疑文件名。
5. 失败时清理已落盘文件；日志只记录必要元数据，不记录敏感全文。

验收标准：路径穿越、伪造扩展名、超大文件、损坏 PDF、空文档测试均能安全失败且不留垃圾资源。

关键函数：`handler.UploadHandler`、`uploads.IsAllowedFile`、`uploads.DetectType`、`uploads.ExtractText`。

### [ ] P0-4 补齐权限隔离与越权测试

原因：项目的亮点是多用户隔离，但必须用自动化测试证明 MySQL、Qdrant、Redis、文件系统和删除链路都不会串用户。

测试矩阵：

- 用户 A 不能查看、检索、删除用户 B 的私有文档。
- A、B 都能检索管理员公共文档，但只有上传者/授权管理员能删除。
- 相同文件名、相同文本和相同 `session_id` 在不同用户间不得串数据。
- Qdrant 查询必须始终包含 `user_id = 当前用户 OR is_public = true`。
- Redis Embedding 缓存可按内容复用，因为只缓存向量、不缓存用户文本结果；后续若缓存检索结果，Key 必须包含 userID/权限版本。
- 文档删除必须使用稳定 `document_id + owner_id`，不能只依赖文件名或推导出的 Chunk ID。

验收标准：上述场景全部自动化通过，跨用户私有数据泄漏率为 0。

### [ ] P0-5 移除配置中的明文数据库密码

原因：`config.yaml` 当前包含明文 MySQL 密码，存在凭据进入版本库或日志的风险。

实施步骤：使用环境变量或本地不提交的配置覆盖；仓库只保留示例占位值；启动时校验必需配置且禁止打印密钥。

验收标准：版本库配置中不存在真实密码、Token 或 API Key。

## P1：提升检索质量与回答稳定性

### [ ] P1-1 将 Markdown 固定长度切块升级为结构化切块

当前问题：`chunker.SplitText` 只按 rune 长度切分，可能截断标题层级、段落、列表和代码块，导致语义不完整；README 中“智能文本切分”的描述目前只是固定窗口。

设计方案：

1. 解析 Markdown AST，识别 H1～H6、段落、列表、表格、引用和 fenced code block。
2. 第一阶段按结构产生原子块，代码块不可从中间切断，并继承完整标题路径。
3. 第二阶段在同一标题路径下合并相邻小块，直到接近 Token 上限。
4. 超大段落再按句子切分；超大代码块按函数/类型边界切分，做不到时再按行切。
5. overlap 优先采用“前一块末尾完整句/父标题”，而非盲目复制固定字符。
6. Chunk 元数据保存 `heading_path`、`block_type`、`start/end`、`token_count`。

为什么先结构切分再合并：固定长度简单但会破坏语义边界；结构切分能保证标题与正文、代码解释与代码尽量共存；合并小块则避免上下文过碎和向量数量膨胀。

合并优先级：结构关系 > Token 大小 > 相邻位置；语义相似度只作为后续可选信号，不能把同标题下逻辑顺序打乱。

验收标准：标题上下文不丢失、代码块不被任意截断、Chunk Token 数不超限；在固定评测集上 Recall@5 不低于基线且引用可读性提高。

关键位置：重构 `internal/chunker/chunker.go`，让 `rag.ImportDoc` 接收带元数据的 Chunk。

### [ ] P1-2 建立可扩展的文档解析器接口

当前实际支持 TXT、Markdown、文本型 PDF，不支持 Word、Excel，也不支持扫描 PDF OCR。Markdown 当前也只是按纯文本读取，没有利用结构。

建议接口：

```go
type ParsedBlock struct {
    Text     string
    Type     string            // heading/paragraph/code/table
    Metadata map[string]string // page/sheet/heading_path 等
}

type Parser interface {
    Supports(filename, mime string) bool
    Parse(ctx context.Context, path string) ([]ParsedBlock, error)
}
```

扩展顺序：

1. Markdown：AST 结构保真，最容易验证切块策略。
2. PDF：保留页码；区分文本 PDF 与扫描 PDF；OCR 作为异步能力。
3. Word：保留标题、段落、表格和列表层级。
4. Excel：按 Sheet/表格区域解析，表头随数据行重复，避免逐单元格碎片化。

验收标准：新增格式只需实现 `Parser` 并注册，无需修改 RAG 主链路；引用能够展示页码、Sheet 或标题路径。

关键位置：重构 `internal/uploads/upload.go`，扩展 `store.VectorChunk` 和 Qdrant payload。

### [ ] P1-3 增加混合检索、阈值与 Rerank

原因：纯向量 TopK 对专有名词、编号、代码符号和精确关键词不稳定；当前也未使用 Qdrant 返回的 score，低相关结果仍会进入 Prompt。

实施步骤：

1. 在 `VectorChunk` 中保留向量相似度分数。
2. 增加最低相关性阈值和“无有效资料”分支，避免硬塞 TopK。
3. 引入关键词/BM25 检索，与向量结果用 RRF 融合。
4. 先召回较大的候选集（如 20），再用轻量 Reranker 排到 5～8 条。
5. 去重相邻高度重合 Chunk，控制 Prompt Token 预算。
6. 所有检索和重排阶段继续强制应用用户权限过滤。

验收标准：在评测集上 Recall@K、MRR、引用准确率明显优于基线；无答案问题的错误引用率下降；延迟增量在预设预算内。

关键位置：扩展 `store.Store.Search` 返回 score；新增 `internal/retriever`、`internal/reranker`；调整 `rag.AskThreeSteps`。

### [ ] P1-4 限制对话记忆并增加问题改写

当前问题：`database.GetSessionHistory` 按时间加载全量历史。会话越长，MySQL 查询数据量与 Prompt Token 数越大，LLM TTFT 和费用都会上升；旧话题还可能干扰当前检索。当前检索使用原始问题，追问“它有什么优点”时可能召回失败。

建议方案：

1. 默认只加载最近 2 轮（4 条消息），SQL 使用倒序 `LIMIT` 后再恢复时间顺序。
2. 对更早历史保存滚动摘要；摘要不直接替代最近原文。
3. 仅当问题包含指代、承接或信息不完整时触发改写；完整独立问题直接检索。
4. 改写产出“独立可检索问题”，保留原问题用于最终回答，避免语义漂移。
5. 用指代追问测试集评估改写前后 Recall 和正确率。

为什么两轮通常够用：多数指代与省略依赖最近一次问答，近两轮可覆盖短期上下文，同时显著减少 Token；但这不是绝对规则，必须用本项目数据验证，长程依赖由摘要或按需记忆检索补充。

验收标准：长会话 Prompt Token 数有明确上限；指代问题 Recall 不低于全量历史方案；P95 TTFT 下降。

关键函数：`database.GetSessionHistory`、`handler.ChatStream`；建议新增 `GetRecentSessionHistory` 和 `query_rewriter`。

### [ ] P1-5 Prompt 与引用防幻觉

实施步骤：

1. 明确区分 system 指令、历史对话、检索上下文和当前问题。
2. 将上传文档视为不可信数据，提示模型忽略文档中的指令，防止 Prompt Injection。
3. 每个 Chunk 使用稳定引用 ID，而不是只按文件名合并来源。
4. 回答完成后校验引用 ID 是否真实存在，并支持返回对应原文片段。
5. 没有超过阈值的上下文时明确拒答，不调用或少调用生成模型。

验收标准：恶意文档中的“忽略系统提示”等内容不能改变系统行为；不存在伪造引用；每个引用可定位到具体文档与 Chunk。

## P1：降低链路延迟并增强可观测性

### [ ] P1-6 拆分每一阶段的耗时与质量日志

当前日志将 Embedding 与 Search 合并统计，只单独记录 LLM TTFT 和总耗时，无法准确定位瓶颈。

需要记录：

- history_load_ms、rewrite_ms、embedding_ms、vector_search_ms、keyword_search_ms
- rerank_ms、prompt_build_ms、llm_ttft_ms、llm_total_ms、request_total_ms
- history_count、candidate_count、filtered_count、prompt_tokens、output_tokens、cache_hit
- request_id、user_id（必要时脱敏）、session_id 哈希、错误阶段

验收标准：单次请求能用 request ID 串起全链路；可统计 P50/P95/P99 和各阶段占比；不得将文档全文、问题全文、Cookie 或密钥写日志。

### [ ] P1-7 减少不必要的大模型调用

原则：先用规则或小模型判断是否值得调用大模型，再按评测结果决定是否引入复杂链路。

策略：

- 独立问题跳过改写；简单事实问题不拆分。
- FAQ/缓存命中直接返回经过权限校验的结果。
- 改写与意图判断尽可能合并为一次结构化输出。
- Rerank 优先使用专用 Cross-Encoder，而不是通用大模型。
- 无有效召回时直接返回受控拒答。
- 入库 Embedding 批量并发执行，但设置并发、重试、限流与幂等。

验收标准：每类请求的大模型调用次数可观测；普通独立问答保持一次生成调用；准确率不下降的前提下 P95 TTFT 达到设定目标。

## P2：工程化与高级能力

### [ ] P2-1 异步化文档入库

- 上传接口只完成校验、落临时文件和创建任务，返回 `document_id`。
- 后台 Worker 执行解析、切块、Embedding、向量写入。
- 文档状态使用 `pending/processing/ready/failed/deleting`。
- 提供进度、错误原因、重试和幂等机制。
- 限制单用户并发任务，防止资源耗尽。

### [ ] P2-2 语义切分自动化实验

1. 先按 Markdown 结构得到候选段落。
2. 对相邻句子计算 Embedding 相似度或主题突变分数。
3. 在低相似度边界切开，在高相似度且同结构的相邻块合并。
4. 同时约束最小/最大 Token 数，防止产生过碎或过大的 Chunk。
5. 对比固定窗口、结构切块、结构 + 语义切块三组的 Recall、MRR、成本和延迟，再决定是否上线。

### [ ] P2-3 是否需要意图路由与问题拆分

只在评测数据证明有收益时增加：

- 闲聊：无需检索，直接进入普通对话或给出能力边界。
- 知识库问答：走 RAG。
- 文档管理：应走确定性 API，而不是让模型直接执行。
- 多跳复杂问题：拆成子问题并行检索，合并去重后统一生成。

风险：每增加一个 LLM 环节都会增加延迟、费用和不可控性。因此要有超时、降级策略，并避免把所有请求都强制走完整长链路。

### [ ] P2-4 从 RAG 演进到 Agent（可选）

当前系统不是 Agent：它执行的是后端写死的“检索—拼 Prompt—生成”流程，模型没有自主选择工具和循环决策能力。

若业务确实需要，可加入只读工具，例如文档列表查询、按元数据过滤检索、知识库统计查询。模型通过结构化 Tool Call 选择工具，服务端负责参数校验、用户鉴权、超时和调用次数限制。删除文档、修改权限等有副作用工具必须二次确认并保留审计日志。

不要为了面试强行 Agent 化。能清楚说明 RAG 给模型补充外部知识，而 Agent 让模型基于目标选择工具并执行多步任务，就已经足够。

### [ ] P2-5 向量库选型形成 ADR

本项目实际选择 Qdrant，面试回答应围绕真实选择：

| 方案 | 优势 | 代价 | 更适合 |
| --- | --- | --- | --- |
| pgvector | 与 PostgreSQL 共库、事务和关系查询方便、部署组件少 | 超大规模与专用检索能力需更多调优；本项目当前还使用 MySQL，迁移成本高 | 已有 PostgreSQL、中小规模、强事务一致性 |
| Qdrant | 专用向量检索、payload filter 直观、部署和 API 较轻量 | 与 MySQL 跨存储一致性需自行处理 | 当前项目、多用户 metadata filter、独立扩展向量服务 |
| Milvus | 大规模分布式检索和吞吐能力强 | 组件、部署、运维和资源成本更高 | 亿级以上向量或高吞吐集群场景 |

要补充的数据：预计文档数、Chunk 数、向量维度、QPS、P95 延迟、备份恢复目标和运维人数。没有这些数据时不要只说“某数据库性能更好”。

## 三、建议的落地顺序

### 第一阶段：让结果可证明

- [ ] 建立评测集和离线评测程序。
- [ ] 给现有固定切块 + 纯向量 Top5 跑出基线。
- [ ] 拆分链路耗时，获得 P50/P95 TTFT 和总耗时。
- [ ] 增加用户隔离、文件上传、导入失败补偿测试。

### 第二阶段：提升检索质量

- [ ] 实现 Markdown AST 结构切块和 Chunk 元数据。
- [ ] 引入相关性阈值、Chunk 去重和 Token 预算。
- [ ] 实验混合检索与 Rerank，用评测结果决定参数。
- [ ] 实现最近两轮记忆和按需问题改写。

### 第三阶段：提升工程可靠性

- [ ] 导入状态机、异步任务、幂等和补偿清理。
- [ ] Parser 插件化并扩展 PDF/Word/Excel。
- [ ] 加入指标、Tracing、限流、超时、重试和降级。
- [ ] 完成向量库 ADR 与容量压测报告。

### 第四阶段：按需求增加高级能力

- [ ] 基于真实问题分布决定是否实现意图路由和多问题拆分。
- [ ] 基于业务动作决定是否增加 Agent 工具调用。
- [ ] 建立线上反馈、坏例回流、评测集版本化和持续回归。

## 四、面试回答时必须避免的表述

- 不要说“只支持 Markdown”：当前代码还支持 TXT 和文本型 PDF；应该说 Markdown 目前没有结构化解析。
- 不要说“使用 pgvector”：当前实现是 MySQL + Qdrant + Redis。
- 不要说“实现了语义切块”：当前是固定 500 rune、overlap 50。
- 不要说“加载最近两轮记忆”：当前代码加载该用户该会话的全部历史。
- 不要说“已经做了改写、拆分、路由、重排”：这些目前都是待办。
- 不要说“这是 Agent”：当前没有模型自主工具调用或行动循环。
- 不要在没有评测数据时声称“准确率提升了多少”或“延迟降低了多少”。先补基线和实验记录。

## 五、完成定义（Definition of Done）

一个改进项只有同时满足以下条件才算完成：

- 有明确问题、设计取舍和失败/降级策略。
- 有代码实现及单元/集成测试。
- 权限过滤覆盖 MySQL、Qdrant、缓存、文件和日志。
- 有评测集对比数据，而不是只展示一个成功案例。
- 有延迟、成本和资源消耗对比。
- README/架构图/接口说明与真实代码一致。
- 能用“背景—方案—取舍—数据—反思”的结构在 2～3 分钟内讲清楚。
